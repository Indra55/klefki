The system map

Klefki is a local encrypted document store with a replication protocol. The clients understand documents and possess decryption keys. The server authenticates requests, stores opaque records, and coordinates delivery. This distinction explains most of the architecture.

This book describes application commit bb78a53, reviewed on 16 October 2026, including the icon and sync-repair changes. Trash, permanent deletion and device-pending reporting are integrated into this source. These are source descriptions, not claims of hosted deployment or physical-device acceptance. Older milestone documents sometimes describe earlier behavior; use the linked implementation records for validation evidence.

A useful analogy

Imagine several branches of your private archive. Each branch can open documents, label them, and create new editions. A courier transports sealed parcels and maintains a delivery ledger. The courier knows parcel IDs, their sizes, and their relationships, but cannot read the documents or labels inside.

In this analogy, clients are archive branches, the server is the courier, ciphertext chunks are parcels, and revisions are editions. The analogy stops at trust: a dishonest courier can hide an entire parcel or replay an old ledger. Encryption detects many altered parcels, but does not prove that the courier showed you every parcel.

The root Go module is klefki. desktop/go.mod defines a second module, klefki/desktop, with replace klefki => .., so its native executable consumes the shared core from this repository. The browser implements compatible behavior in TypeScript; it does not call the Go crypto package.

The document journey

Our recurring example is electricity-bill.pdf, a 9 MiB PDF placed in a Bills folder. It is an invented teaching fixture, not a real user document.

  1. An account creates a random master key and password/recovery wrappers.
  2. Import creates a logical object ID, a revision ID, a content file ID, and a file key.
  3. Metadata and three content chunks are encrypted locally.
  4. A database transaction saves ciphertext and marks the revision pending.
  5. Sync uploads missing chunks, then publishes the revision.
  6. Another client verifies all records and commits the complete revision locally.
  7. The receiving client acknowledges durable receipt.
  8. Desktop/CLI extract text and store encrypted search sidecars.

Each step has different failure rules. Reading a chunk is not committing a document. Uploading chunks is not publishing a revision. Receiving a response is not acknowledging durable storage.

Check your understanding

Why can two devices share encrypted documents without the server having the master key? Because they share the encrypted account state and unlock the same master key locally; the server only moves the encrypted records.

Startup, account creation, and unlock

There are two different meanings of initialization: starting a process, and creating a cryptographic account. Starting a server does not create a client master key. Starting desktop does not automatically unlock its database. Keeping these separate helps you understand what can run while the vault is locked.

Server startup

cmd/klefki-server/main.go parses the listener address, data directory, TLS options, optional web directory, and relay quota. It rejects incompatible listener modes before opening storage. The default listener is 127.0.0.1:8080; normal operation requires a certificate and key. -dev-http permits HTTP only on a literal loopback address. -proxy-http supports an HTTPS reverse proxy and requires the forwarded HTTPS condition enforced by the server.

server.Open creates a private data directory and SQLite file, enables WAL and foreign keys, builds base tables, and runs migrations for sync, relay, deletion, and status. It opens a disk blob store and registers the HTTP routes. It does not decrypt a document during startup: there is no master key available to it.

The HTTP server bounds header size and timeouts. It listens until a listener error or interrupt/termination signal. On shutdown it allows a ten-second graceful shutdown window before closing the listener. If a built web directory was supplied, a handler serves that app and API from the same origin.

CLI startup

cli/main.go dispatches commands to local encryption, sync, search, model, and backup handlers. It defaults the account path to .klefki/account.v1; the document database normally lives beside it as local.db. CLI commands load only what they need, rather than maintaining one permanently unlocked process.

Passwords are read from a hidden terminal prompt or an explicit secret file. They are not literal command-line secret values. A secret file strips one optional terminal line ending while preserving other bytes. This matters because password, password, and password derive different keys.

Creating an account

crypto.NewAccount generates the account ID, a random master key, a random recovery key, and a salted Argon2id descriptor. It derives the password keys, encrypts the master key under the password KEK, and encrypts that same master key under the recovery key. The account file contains these public descriptors and encrypted wrappers.

The CLI writes the recovery code to an explicit private destination. Desktop's native wrapper selects a directory and confirms the recovery path. The recovery code is a second key to the archive, so the useful safety property is separate storage, not merely having another file beside the vault.

Desktop session startup

The Wails executable owns a core/desktop.Service. The service loads configuration and starts maintenance/scheduling logic while keeping the account locked. On password unlock it loads account.v1, unwraps the master key, derives the sync credential, and starts an unlocked session. Recovery unlock recovers the master key without deriving a password-based network credential.

The current password path calls Account.Unlock and then derives password keys again to obtain the auth credential. That is an implementation detail with a performance consequence: the expensive KDF can run twice in that path. This description follows current source rather than assuming a single combined derivation.

An unlocked session owns the store, keys, cancelable context, network state, and optional model. Generation numbers distinguish sessions, so late work from an older session cannot be treated as current work after a lock/unlock cycle.

Why opening and unlocking differ

Think of opening a storage room versus obtaining its keys. SQLite can open tables containing ciphertext without revealing filenames. Unlock produces the master key in memory; only then can metadata be authenticated and decoded. Encryption protects private payloads inside the database, rather than encrypting the whole SQLite file.

Passwords, authentication, and the key hierarchy

Klefki separates three jobs: proving access to the server, unlocking the document collection, and decrypting one content revision. Separate keys make these jobs explicit and reduce the consequences of confusing them.

The keyring analogy

The master key is the archive's keyring. Each document content revision has its own small key. The password opens a sealed box containing the keyring. The recovery code opens a second sealed box containing the same keyring. The server login credential is a courier access badge: it authorizes fetching parcels but does not open them.

The analogy is precise in one useful way: changing the outer box's lock need not change every document lock. It is incomplete in another: once someone copies a keyring, changing your password cannot make that copy disappear.

Derivation, byte by byte

The 27-byte KDF descriptor contains version 1, algorithm identifier 1, memory 65,536 KiB, iterations 3, parallelism 1, and a random 16-byte salt. The implementation accepts this exact profile and rejects others before expensive work. This prevents an untrusted descriptor from silently selecting a weaker profile or requesting unbounded resources.

K = Argon2id(UTF8(password), salt,
             memory=65536 KiB, iterations=3, parallelism=1,
             output=64 bytes)
KEK      = K[0:32]
auth_key = K[32:64]

credential = HMAC-SHA256(auth_key,
                        "vault/auth/v1\0" || account_id)
verifier   = SHA256("vault/auth-verifier/v1\0" || credential)

Argon2id makes each password guess consume memory and computation. A salt makes equal passwords in different accounts yield different keys. Neither guarantees a weak password is safe against offline guessing.

Go's KDF memory parameter uses KiB. Libsodium's TypeScript call uses bytes, so the matching number is 67,108,864. Matching the units is required for the two implementations to derive identical keys.

Passwords are UTF-8 without normalization, trimming, or case conversion. The byte limit is 1,024. Invalid Unicode is rejected. These rules are compatibility requirements: changing string processing on one client could make an existing account impossible to unlock there.

Keys created randomly

The master, recovery, and file keys are independently random 32-byte values. They are not document hashes and are not extracted from filenames. New file content gets a fresh file ID and key. A metadata-only edit can reuse the existing content key because the content is unchanged.

The KEK encrypts the master key in the password wrapper. The recovery key encrypts it in the recovery wrapper. The master key encrypts metadata and wraps file keys. File keys encrypt chunks. IDs and nonces are public context, not substitutes for secret keys.

Authentication is separate from encryption

The server receives the derived credential over TLS and retains its domain-separated verifier. A leaked credential can authorize server access but does not directly recover the KEK or master key. The server can still capture a submitted credential, and the protocol is replayable bearer authentication rather than a password-authenticated key exchange.

Recovery uses the random key encoded as vlt1- plus 52 uppercase Base32 characters, for 57 characters total. This code does not go through Argon2id. Strict canonical decoding rejects altered case, padding, whitespace, and nonzero pad bits. A syntactically valid typo fails when the master wrapper is authenticated.

Password rotation: design versus a command

The hierarchy permits generating a new salt and KEK, rewrapping the existing master key, and replacing the server credential. It does not require re-encrypting every document. That is a property of the hierarchy; it should not be mistaken for a shipped complete password-rotation workflow. The inspected CLI command dispatcher does not expose such a command.

Authenticated records and chunked files

Encryption must establish both secrecy and context. A decrypted block is useful only if it belongs to the expected account, object, purpose, and file position. Klefki packages those expectations in authenticated envelopes.

Sealed parcels with authenticated labels

Imagine a sealed parcel whose label says account A, file F, chunk 2, final=false. The label can be visible, but opening the parcel verifies that its label has not changed. This is additional authenticated data, or AAD: information checked by authentication without being hidden by encryption.

Klefki uses XChaCha20-Poly1305, with a 32-byte key, 24-byte nonce, and 16-byte authentication tag. A fresh random nonce is used for each new encryption. Retrying a transfer sends the already-produced ciphertext; it does not create a new encryption merely because the network failed.

Common record kinds

Kind Payload Key Bound object
1 Master key Password KEK Reserved zero ID
2 Master key Recovery key Reserved zero ID
3 File key Master key File ID
4 Metadata JSON Master key Logical object ID
5 Content chunk Revision file key File ID plus index/final state

Kinds 1–4 have a 58-byte header: version, kind, 16-byte account ID, 16-byte object ID, and 24-byte nonce. AAD is the literal domain vault/record/v1\0, the complete header, and any kind-specific extra bytes. The password wrapper additionally authenticates the exact KDF descriptor. Kinds 1–3 carry 32-byte payloads and therefore occupy 106 bytes each.

The caller supplies expected account/object/kind. Trusting only a record's own header would allow a perfectly authentic record from the wrong context to be accepted.

Chunk layout

Offset Bytes Meaning
0 1 Version
1 1 Kind 5
2 16 Account ID
18 16 File ID
34 8 Zero-based chunk index
42 1 Final flag, exactly 0 or 1
43 4 Plaintext length
47 24 Nonce
71 Variable Ciphertext followed by 16-byte tag

All integer fields are big-endian. A chunk occupies 87 + plaintext_length bytes. Maximum plaintext per chunk is 4,194,304 bytes, exactly 4 MiB.

Worked example: a 9 MiB bill

Authenticated metadata: size=9,437,184, chunk_count=3
chunk 0: 4,194,304 plaintext bytes, final=0
chunk 1: 4,194,304 plaintext bytes, final=0
chunk 2: 1,048,576 plaintext bytes, final=1
Total chunk-envelope overhead: 3 × 87 = 261 bytes

An 8 MiB file has two full chunks, with the second marked final; it has no extra empty chunk. A zero-byte file still has one final empty chunk. These cases prevent ambiguous framing.

Complete-file authentication

The reader checks consecutive indices, expected account and file ID, permitted lengths, exactly the expected final position, total size/count, and no extra trailing records. Altering a final flag fails AAD authentication. Removing a final chunk can leave earlier tags valid, so complete-file validation remains necessary even after individual chunks authenticate.

Changed content gets a fresh file key. Mixing chunks from two content revisions therefore fails authentication under the selected revision key. Replaying an entire old, valid metadata/key/chunk set is different: the cryptography alone does not prove freshness.

Metadata and containers

Metadata is UTF-8 JSON encrypted as exact bytes. Parsers reject duplicate fields, malformed Unicode, invalid IDs, and inconsistent size/count fields. Metadata also includes optional trash timestamps and previous-parent information. Those additions must not be confused with the original minimal metadata schema in older docs.

The account container VLTA version 1 is exactly 260 bytes. The standalone encrypted-file container VLTF contains IDs, a wrapped file key, a bounded metadata record, and chunk records. The sync database uses the same cryptographic records without requiring every document to be stored as a VLTF file.

Local storage, transactions, and revision graphs

The database holds encrypted records and the bookkeeping needed to replicate them. It is useful to separate a document's stable identity from an edition's identity and from a particular encrypted content stream.

Four identities

Identifier Lifetime Example role
Account ID Account lifetime Which archive owns the records
Object ID Logical document/folder lifetime The bill despite later renames
Revision ID One edit A specific version of that bill's metadata/content
File ID One content encryption Which chunks and wrapped key belong together

A rename creates a revision but can retain the file ID. Replacing document bytes creates a revision and fresh file ID/key. A folder has metadata and revisions but no document chunks.

The ledger analogy

Instead of erasing an entry and writing over it, keep an append-only ledger of editions. Every edit says which edition it started from. That produces a graph of parent/child relationships. In normal history the graph is a line. Two offline edits produce a fork.

A head is a revision with no child. The head query finds revisions for which no other revision names them as its base. If an object has multiple heads, each is exposed as a conflict copy. The implementation does not select a winner by timestamp or arrival order.

For example, revision R0 is the original bill. Desktop creates R1 adding the tag Utilities. A disconnected browser creates R2 marking the same R0 as favorite. Both R1 and R2 remain heads after sync. Editing R1 later does not silently erase R2. There is no automatic field-wise merge merely because these particular edits could appear compatible.

SQLite representation

The main tables are:

local_state(singleton, version, account, remote, cursor)
revisions(ordinal, id, object, base, metadata, file_key, pending)
chunks(file, idx, data)

Additional tables track stable relay identity, provenance, deletion state, and the versioned local pending-work report. ordinal orders local insertions; server sequence is a different ordering. metadata, file_key, and chunk data contain encrypted records. IDs, bases, queue flags, remote origin, and cursors are readable database structure.

Opening a store checks its account binding. Binding it to a server permits the initial origin or the existing origin; an accidental attempt to sync the same database to a different server fails. Use a separate store for another account/device. OpenExisting refuses a missing or uninitialized database, so backup tooling cannot mistake a new empty database for a successful recovery of the old one.

Atomic offline edits

PutContext encrypts content into chunks and inserts chunks, metadata/key pair, revision, and pending flag inside one transaction. A short source stream, extra bytes, cancellation, or transaction failure causes rollback. You do not get a visible half-document with no pending queue entry.

This is like completing a bank transfer in one transaction: the document and the intention to replicate it belong together. A later network failure leaves the durable local edit pending. Network availability is not a prerequisite for editing.

WAL and store ownership

The store enables SQLite WAL, foreign keys, a busy timeout, and current-source secure deletion. It uses one database connection and synchronization around operations. The operating-system lease protects the local store from competing processes; opening its canonical path takes a lock file lease. This is especially relevant when CLI and desktop might otherwise open the same database simultaneously.

WAL records database changes before incorporating them into the main database file. Copying only local.db while it is live can miss committed data still in local.db-wal. The snapshot chapter explains the correct backup path.

Encryption is at the record layer. There is no SQLCipher page encryption here. Secure-delete and compaction settings do not establish forensic erasure on SSDs, filesystem snapshots, hosting backups, or prior exported copies.

Import, edits, folders, trash, and deletion

All normal document changes become encrypted revisions. Understanding which changes replace bytes and which replace only metadata explains both performance and conflict behavior.

Importing the bill

Desktop's Service.Import schedules a cancelable file operation. It reads a selected source, validates metadata and parent relationships, and passes content to Store.PutContext. The store generates fresh content identifiers and a random file key, wraps that key, encrypts metadata, streams encrypted chunks into SQLite, and commits the pending revision.

The import path does not need a plaintext staging copy of the entire document in the local sync store. Browser import behaves differently: its store API receives a Uint8Array and prepares chunks in memory before the IndexedDB commit. The common envelope format does not imply equal memory use on the two clients.

Renaming is cheaper than replacing content

Store.Edit loads the selected base revision, authenticates its metadata/key association, verifies that the base has no existing child locally, updates permitted metadata fields, encrypts new metadata with a fresh nonce, and inserts a child revision. It reuses the previous wrapped file key and stored content chunks.

Thus renaming electricity-bill.pdf to September-electricity.pdf does not encrypt another 9 MiB. Replacing the PDF with edited bytes does: PutContext generates a fresh content key/ID and ciphertext stream. Both actions still produce a new revision, so both can conflict with another offline edit.

Folder trees are metadata references

A folder is a metadata object with type folder. A child's parent is a folder's object ID. Folders are not filesystem directories on the server; folder names and parent relationships within metadata are encrypted. The outer revision graph is visible separately.

Desktop validates parent selections and rejects cycles or unsuitable parents. A folder rename is another metadata revision. Moving a document changes its parent reference. The relevant model is a graph of logical objects, not a server filesystem path derived from a document name.

Trash is a reversible change

The special trash folder is identified by the reserved tag klefki:system:trash. Moving a document or folder there is a metadata operation. Descendants inherit the ancestor's trash position. Their chunks remain available until permanent deletion, so restoration does not need to retrieve a lost plaintext file.

The metadata records trashed_at and trash_previous_parent. Previous-parent information makes restoration more meaningful than moving everything to the root. The source's retention constant is 30 days. Dates use milliseconds in the encrypted metadata, matching browser date conventions.

Permanent deletion is a separate protocol

Deletion is present in the base source. This section explains its implementation; the trash guide records behavior and acceptance boundaries. Statements that deletion is unimplemented belong to the original M3 baseline.

Deleting a revision alone would allow an old offline copy to reintroduce the object. The new code instead records a permanent object fence. Imagine crossing an archive item off a registry that every branch must consult before accepting old deliveries.

PreviewDeletion gathers the selected trashed objects and descendants and includes their current heads. DeleteTrash recomputes those targets before erasing them. If the heads changed after the preview, deletion fails as a conflict instead of applying a stale decision. It also blocks permanent deletion in a bound store whose server does not support deletion.

The deletion wire record contains an object ID, folder flag, file IDs, and optional expected heads. A separate deletion feed has its own epoch and cursor. Sync processes fences before ordinary revisions and again at completion, so an old revision for a fenced object can be skipped while advancing the ordinary cursor.

Local erasure removes revisions/chunks and prunes encrypted search/analysis records that refer to deleted objects. The source includes compaction. Automatic expiry avoids unresolved conflict subtrees. These mechanisms explain intended logical deletion; they do not erase other devices' offline copies, preexisting backups, or storage-provider snapshots.

The server: authentication, scope, and ciphertext publication

The server is an authenticated ciphertext service. It can validate public framing, account scope, revision links, and storage rules. It cannot authenticate private plaintext with AEAD because it does not have document keys; clients must perform that verification.

Signup and login

Signup sends the account ID, KDF descriptor, two encrypted master wrappers, and derived credential. The server validates sizes and envelope headers and computes a credential verifier. It inserts the account and initial device session in one transaction. Duplicate registration returns a conflict rather than replacing the account.

Login sends the account ID and credential. The server computes the candidate verifier and compares it in constant time with the stored verifier. A successful login creates a random 32-byte session token and random device ID. The server retains a SHA-256 token hash and expiry, rather than the raw token. Default session lifetime is 30 days.

Authenticated requests use Authorization: Bearer TOKEN. Middleware hashes the token, finds a nonexpired session, and places account/device identity in the request context. Handler queries use that account identity. A client-supplied file ID must never establish account ownership by itself.

Think of an archive clerk checking an access badge, then looking only in the badge owner's shelves. The opaque parcel number identifies an item within those shelves; it does not authorize entering another person's shelves.

SQLite plus disk blobs

The server database contains accounts, session hashes, encrypted metadata, revision/change records, delivery cursors, and extension state. Chunk payloads live in an account-scoped disk blob store. This separates large binary transfers from relational bookkeeping.

Chunk publication is immutable. Repeating an upload with identical ciphertext is safe. An attempt to reuse an existing location with different bytes returns a conflict. A server restart or a lost HTTP response therefore does not require inventing a new file revision to retry a chunk.

Revision publication verifies structural expectations and base-object relationships, then appends one sequence to the change log transactionally. It is also idempotent for an identical revision ID and body. A reused revision ID with changed bytes or links fails. Chunks may exist before a revision is published; that is intentional staging, not yet a complete visible edit.

Limits and transport

Request decoding is bounded and rejects malformed input. The rate limiter is a token bucket: by default it allows a burst of 120 and replenishes 120 tokens per minute. Login additionally checks an account bucket; normal request handling applies its other limiter scope. These are request budgets, not a claim of 120 successful logins per minute for every situation.

Normal clients use TLS and reject redirects. Development HTTP is loopback-only. Reverse-proxy mode requires correct trusted deployment configuration; forwarded headers are not magically authenticated if the backend is exposed directly to attackers.

Request logs deliberately avoid secret bodies and document contents. The server still sees operational data: IDs, sizes, timing, account relationships, delivery activity, and peer addresses. Client-side encryption protects private payloads, not all traffic metadata.

Offline synchronization, cursors, and failure recovery

Sync is a sequence of durable transitions. Its main safety rule is that a receiving client acknowledges progress only after saving a complete authenticated revision. A cursor is a bookmark in a delivery ledger, not a cryptographic proof of the ledger's honesty.

Push in dependency order

Pending revisions are selected in local insertion order. A locally created base therefore precedes its child. Before upload, the Go client checks the local revision's content integrity. It inventories existing remote chunks and uploads missing ones, using the stored ciphertext exactly.

After all chunks have been accepted, the client sends PUT /v1/sync/revisions/{id}. Only a successful immutable publication clears the local pending flag. Suppose all three bill chunks arrive but the last response disappears: retry inventories the server, finds those chunks, and proceeds to publication. Suppose the publication succeeded but its response disappeared: repeating the same revision returns the original sequence.

Pull from the local bookmark

The client requests changes after its local durable cursor, not the server's recorded acknowledgement for a session. A new local store starts at zero even if some old session acknowledgement is ahead. Acknowledgement records what a client reported; it does not populate an empty local database.

The change page contains at most 16 records. Sequences increase but need not be consecutive, because the server log is shared across accounts. Account-scoped queries prevent another account's changes from being returned.

For each change, the client validates identifiers, authenticates encrypted metadata and file-key association, fetches the expected chunks, and checks their entire-file context. It commits the complete revision and updated local cursor together. Earlier good revisions can remain committed if a later revision fails, but the failed revision does not become visible or advance its bookmark.

Receipt before acknowledgement

Imagine signing for a shipment only after you have inspected every parcel and put it safely into your warehouse. Sending the receipt while the goods are still on the loading dock would let a relay delete the only available copy too early.

remote download
    -> authenticate every required record
    -> commit chunks + revision + cursor locally
    -> PUT server acknowledgement

An acknowledgement failure is recoverable. The local cursor survives and can be acknowledged again. A download failure retains the previous local cursor. Uploaded chunks resume individually; an incomplete downloaded revision is retried as a revision rather than being exposed as a partial document.

Retry rules

Network failures, HTTP 408, 429, and most server 5xx responses can be retried. 507 (insufficient storage) is an explicit exception: the client must resolve the relay/storage condition instead of blindly repeating it. Default Go behavior uses up to four attempts, exponential delays beginning at 250 ms, and a 30-second backoff cap. An integer Retry-After up to 120 seconds can override that cap. All waits observe cancellation. Configured attempts are capped at ten.

Authentication failures, conflicting immutable records, malformed data, and failed cryptographic checks do not become successful by repeating them blindly. The stored pending queue remains available for a future sync after the real issue is resolved.

Sync additionally exchanges deletion fences before normal transfer and again at completion. A fenced object is not resurrected by replaying its older revisions. This adds requests beyond the published pre-deletion benchmark flow.

Two kinds of concurrency

Only one sync pass runs against a Go store at a time through syncMu. Revisions publish sequentially because parents and cursors need ordered reasoning. Inside a revision, up to four chunk transfers can run concurrently. Results are consumed in index order; network completion order does not determine authenticated file order.

Content integrity and honest-server conflict handling are strong local rules. Server sequences and parent links themselves do not establish authenticated global history. A malicious server's omitted revisions or complete rollback remain outside the protocol's freshness guarantees.

Presence, provenance, and durable receipt differ

The status extension separates a device's live activity from its durable cursor. Presence reports client kind, phase, opaque revision ID, transfer direction, and byte progress under the authenticated account and stable device identity. A client may be uploading now while its durable receipt cursor still describes only earlier committed revisions.

The server stores client kind and last-contact time in SQLite, but keeps live phase/progress in memory. Status uses a live-presence window of 45 seconds; after restart, the persisted last-contact record survives while live phase becomes unknown. This prevents a stored “downloading” value from pretending an interrupted process is still active.

Provenance distinguishes an edit's original device from the client that published it. They can differ when a retained local copy reseeds a relay. Attribution is opaque operational bookkeeping, not an authenticated authorship signature. Private device nicknames remain local. Progress objects inside clients can include decrypted filenames, but those names are not part of the server presence payload.

NeedsSync compares server/local state to decide whether work is due. A green-looking activity state would never substitute for the transaction-and-acknowledgement ordering above. The current deletion extension also adds its own sequence signal to status so a device can notice deletion work even when ordinary revision progress is unchanged.

Pending work can outlive live presence

The integrated device-state extension adds an advisory report: a stable device ID, a monotonically ordered version, and a boolean indicating pending revisions or deletions. The server stores the report and its receipt time in SQLite. Unlike transient presence, a report can survive the source device closing and a server restart.

The local store snapshots pending work and the report version transactionally. Clients advertise/report this state through the existing monitoring flow when the server supports it. A late report cannot overwrite a newer version. Reports contain no document names or contents.

A device that last reported pending work can therefore remain labelled as having changes waiting even after another device has received all revisions currently on the server. This separates server delivery from unpublished local changes. The report is advisory: changes made entirely offline cannot be known remotely until that source reports them, and a saved report is not a backup or proof of complete synchronization. See sync activity for freshness and interface wording.

Staging a fresh desktop copy safely

The desktop FreshDownload operation downloads into a separate private directory beside the selected store. It keeps the encrypted account file and original database intact. It requires a server connection and an authenticated unlocked session, and refuses recovery-only access, pending local work, or an active sync. It authenticates the original store first, so it is not a bypass for corrupt local ciphertext.

The operation logs in to the existing remote account; it never signs up again or switches the server's storage mode. Its staging store has its own durable cursor and stable device identity. A failed or interrupted download retains that staging path so another attempt resumes the same store and device instead of enrolling another relay device each time. In temporary relay mode, linked devices may need to provide retained history before this new copy can finish.

After sync, the client authenticates the staged store and checks coverage against every revision known to the original store. A missing revision is accepted only if its object has a deletion fence in the new store. It does not select an incomplete replacement. This establishes coverage of known local history, not proof that an untrusted server disclosed every unknown revision.

Only after those checks pass does the service persist the new selected store path and remember the original as previousStorePath. It then detaches the old session, cancels work, and locks; the next unlock opens the verified copy with the existing account. Sync-pause preference is preserved. A download, validation, cancellation, or configuration-save failure leaves the original selected. The retained original is not automatically deleted.

This recovery flow provides a checked fresh-copy option. Its implementation alone does not establish the cause of a particular Linux stale-sync report or demonstrate that report was reproduced. See sync activity for user-facing recovery guidance and validation limits.

Temporary relay, batching, and transfer performance

Persistent mode keeps server payloads. Temporary relay mode removes delivered ciphertext once all linked devices have acknowledged saving it, with at least two devices required. Local history and backups become especially important because the relay is a delivery buffer rather than a permanent archive.

Session identity versus store identity

Logging in creates a session device ID. Temporary relay needs an identity that survives login/logout and process restarts, so each local store also owns a stable random relay device ID. These are related but different identifiers.

The relay records device membership, account mode, epoch, delivery cursors, and revision digests. A server epoch identifies a particular relay state. If an ephemeral host loses state, a new epoch lets clients reset server progress and offer retained local history again. Existing clients provide ciphertext; the server does not reconstruct missing documents from a password or recovery code.

The parcel-locker analogy

Two devices use a shared locker. Device A puts in encrypted parcels; device B collects and durably stores them. Only after the delivery requirements are satisfied can the locker empty. A newly linked device after cleanup needs an existing client to refill the locker from its own archive.

An acknowledgement is a trusted client's assertion, not mathematical proof of possession. An unavailable linked device can prevent cleanup. Forgetting a device changes those delivery requirements, so it has stronger consequences than changing a private device nickname.

Why small files can feel slow

Transfer time is roughly:

sequential_request_count × round_trip_latency
+ payload_transfer_time
+ local encryption/storage/verification time

This is an intuition, not a precise network simulator. Ten sequential requests at about 300 ms each can consume roughly three seconds before payload work is significant. A fast disk or stronger CPU cannot remove remote round trips.

The published October optimization combined relay preparation with a batch of history checks. POST /v1/sync/relay/prepare carries device state and up to 256 revision IDs. Additional batches use /need-batch. Legacy /device and /need remain with 404/405 fallback for compatible older servers.

The measured pre-deletion 84-revision no-edit path went from ten production requests to three: preparation, changes, and durable acknowledgement. Current deletion and device-state exchanges add protocol work; that historical request count does not describe every current sync pass.

Four chunks at once

Go and browser clients use bounded windows of four transfers. A 9 MiB file has only three chunks, so one window can handle its content transfers. A 64 MiB file has sixteen chunks, handled in four windows. Four 4 MiB results imply about 16 MiB of payload buffering per full window, plus envelopes and other memory; this is an estimate of window payloads, not the application's total memory ceiling.

A failed transfer cancels siblings and waits for them before returning. Results are then processed in index order. Shared Retry-After cooldowns keep parallel workers from independently hammering a throttled server. Revision publication stays sequential.

Account-scoped locking

The server uses reference-counted locks keyed by account. Quota checking, publication, and cleanup for one account are serialized. Bounded upload reads and buffered download writes occur outside that critical section. Otherwise a slow network read while holding a global lock would block unrelated accounts and neutralize client concurrency.

This does not imply unlimited server parallelism. SQLite still uses one connection in this implementation, disk I/O still costs time, and account operations still coordinate under their lock.

What measurements establish

The repository's October report records no-edit Go time moving from 3.618s to 1.034s and 64 MiB browser upload from 40.585s to 18.801s in hosted sweeps. These are historical session measurements of the combined update, with stated automation/history limits. They have not been rerun for this guide's current source snapshot and are not a long-term latency guarantee.

Unlocked sessions, cancellation, and convenience access

Locking is a resource transition. It must stop operations, detach private state, close owned resources, and clear key copies. Merely drawing a lock screen would not establish that boundary.

Ownership and generation numbers

core/desktop.Service owns an optional unlocked session. That session holds the master key, sync credential, local store, operation context, remote session, and optional model. The service's generation increments when the session is invalidated. Results/events carry generation information so late completions do not belong to a newly unlocked session.

Think of lending a contractor a keycard valid for one shift. Canceling the shift invalidates outstanding work. A later shift gets a new identity even if it uses the same room. Checking only “the room is currently open” would accidentally accept yesterday's job result.

Lock order

The current Lock implementation detaches the session, increments generation, cancels its context, resets scheduling state, and emits the locked event before waiting for active work. It then waits for serialized work and network completion, closes the optional model, wipes master/credential arrays, and closes the store. It attempts server session revocation asynchronously with a five-second timeout.

Cancellation before waiting avoids a deadlock-like lifecycle where lock waits indefinitely for work that has not been told to stop. A failed revocation does not restore local keys, but can leave the remote session valid until expiry or later revocation.

Go clearing and JavaScript memory wiping are best effort. The runtime, immutable strings, native libraries, swap, or earlier copies can retain sensitive data. The design minimizes lifetime; it does not claim guaranteed physical erasure of every copy.

Scheduling while unlocked

The desktop watcher evaluates inactivity every second, requests periodic background sync at sixty-second intervals, and checks trash maintenance hourly in the current source. Network monitoring, local changes, and explicit sync requests also influence scheduling. These timers are not a daemon that can decrypt and sync a locked vault.

File operations use contexts and cancellation. The work lock serializes sensitive store/model operations, while network lifecycle tracking lets locking wait for them to finish safely. Large operations therefore have both a progress lifetime and a secret-owner lifetime.

Linux fingerprint convenience

Klefki delegates biometric verification to fprintd over the system D-Bus. It does not derive a cryptographic key from the fingerprint image or enroll templates. After password unlock and successful verification, it saves a record containing the master key and sync credential in the OS secret service/keyring, bound to the selected account.

On later unlock, a successful system verification permits loading those saved keys. Password and recovery remain other access routes. The security boundary is the OS keyring and session permissions: another app able to read an unlocked keyring may access stored unlock secrets. Fingerprint verification is an application convenience gate, not a claim of hardware-sealed document encryption.

Browser passkey PRF

The browser route uses a different mechanism. WebAuthn PRF produces a repeatable secret for a credential and input after required user verification. Klefki derives a 32-byte wrapping key with HKDF-SHA256 and encrypts a 64-byte payload containing master key plus sync credential with XChaCha20-Poly1305.

The local wrapper binds version, origin, relying-party ID, account-file hash, credential ID, salt, and nonce-related record state. Loading checks origin/account binding; assertions check the challenge, credential ID, relying-party hash, presence, and verification flags. This is local convenience unlock, not a new server login protocol.

The wrapper lives in localStorage as ciphertext. Secure origin and compatible authenticator/browser PRF support are required; a domain or localhost is used rather than an IP origin. The provider may use fingerprint, face, or PIN and may sync passkeys. Removing local setup does not revoke a copied valid wrapper.

Browser persistence and native runtime boundaries

The browser client is a second implementation of the encrypted store and protocol. Its important technical differences are storage APIs, transaction lifetimes, executable-code delivery, and memory behavior. This chapter concerns those mechanics, not the interface.

IndexedDB as the local ciphertext database

Store.open uses an account-specific database name, klefki-v1- followed by the account ID. The database version is 2. Object stores hold state, revisions, chunks, and deletion fences. Account initialization checks that the stored account descriptor/wrappers match the chosen account.

Each revision contains encrypted metadata, optional wrapped file key, pending flag, insertion order, and optional origin information. Chunks are keyed using file ID and index. The state store holds account state, cursor, bound origin, stable relay identity, and the versioned pending-work report.

Store.commit writes revisions, chunks, state, and deletion checks in one read/write transaction. It validates base ownership, immutable retries, and current local edit assumptions. A received sequence is saved in the same commit as its accepted ciphertext.

Async request success is not transaction success

IndexedDB has request events and transaction events. One successful put request does not mean the entire transaction committed. Klefki's transaction helper waits for oncomplete and treats abort/error as failure.

An analogy is a restaurant order: the kitchen accepting each item is different from the complete order being delivered. A later abort can invalidate earlier successful requests in the same transaction.

IndexedDB transactions also have lifetimes tied to queued database work. Arbitrary network waits inside them can let a transaction become inactive. The browser sync path gathers/authenticates received data before local publication. The Go path can hold a SQLite transaction across downloads; identical protocol guarantees do not require identical storage choreography.

Why the browser can use more memory

The store's put receives complete bytes and builds encrypted chunks in memory. export fetches chunks and produces authenticated plaintext for the caller. The Go streaming path can process document content in bounded pieces. Both enforce the format's 4 MiB chunk rule, but that does not make the browser's whole-document workflow a streaming pipeline.

Stored ciphertext surviving browser restart does not imply storage is guaranteed permanent. Browser quota, site-data clearing, private browsing behavior, and eviction can remove the database. Sync copies and separately verified backups remain necessary.

Service worker responsibilities

web/scripts/sw.mjs generates a content-hashed app-shell cache. The worker handles selected same-origin GET resources. It explicitly avoids /v1/ API requests, search-bearing URLs, and unrelated origins. Model assets use a fingerprint-specific cache. Activation removes old app-shell caches and claims clients; explicit update activation can invoke skipWaiting.

This worker enables executable shell assets to be available offline. It does not store master keys, perform OCR, or act as a locked-vault sync daemon. The encrypted document database and the app-shell cache have separate purposes.

Code delivery is a trust boundary

A browser origin supplies the JavaScript that receives passwords and handles unlocked keys. A compromised origin can serve malicious code on a later load/update, even if every document on the server is encrypted. HTTPS protects transport to that origin; it does not make the origin incapable of abusing its own application code.

The native desktop executable instead embeds built assets using Go embed and binds Go methods through Wails. Its filesystem access and secret-service integration live behind the native wrapper/core. Desktop still requires trusted builds and distribution. Rebuilding native code without rebuilding embedded assets can ship an older client runtime; make linux-build deliberately builds assets first.

Local text extraction and OCR

Search cannot match document content until content has been converted into text. Klefki performs that conversion on an unlocked trusted client, then encrypts the index produced from it. The server never needs a plaintext search copy.

Three input paths

Supported UTF-8 text extensions include .txt, .md, .csv, .json, and .log. The extractor rejects invalid UTF-8, NUL bytes, or input above its text limit. Unsupported formats can still exist as encrypted documents; they receive metadata search coverage rather than full content extraction.

PNG/JPEG inputs are decoded and re-encoded as PNG before being passed to Tesseract on stdin. Tesseract can interpret some inputs as filename lists, so passing raw bytes from a mislabeled upload would create a dangerous ambiguity. Canonical re-encoding ensures the tool receives actual image data. Pixel dimensions are checked before full decoding.

PDFs use Poppler tools plus Tesseract. A PDF can contain selectable text, scanned images, or both. Choosing “has any text, therefore skip OCR” would miss content printed inside images on an otherwise textual page.

PDF pipeline

  1. Stage the PDF in a private temporary directory with private file permissions.
  2. Use pdfinfo to read page count and enforce the page cap.
  3. Use pdfimages -list to inspect page images and bounded dimensions.
  4. Run pdftotext once for the document, then split extracted text by page.
  5. OCR page images when applicable, or rasterize the displayed page for scans/masked composites.
  6. Merge OCR terms with selectable text and return bounded output.
  7. Remove temporary files and wipe available byte buffers.

When a page has no useful text or includes image masks/composites, it uses pdftoppm to render the page as displayed before OCR. That preserves rotation and visual compositing better than assuming an extracted image alone represents what the reader sees.

Worked example: a mixed bill

Suppose the PDF has selectable text saying “Electricity statement” and a scanned image containing meter ID MTR9021. pdftotext finds the heading but not the meter ID. Image OCR contributes MTR9021, enabling a precise later keyword match. Merging avoids inflating frequency counts by indiscriminately duplicating words already present in selectable text.

The extractor caches OCR results for repeated PDF image object identities within a document. A repeated logo does not need to start Tesseract on every page. Limits still apply to cached text, pixels, and page content.

Resource bounds

The current extractor permits at most 64 MiB per supported document, 2 MiB extracted text, and 100 PDF pages. Image decoding caps one image at 16 million pixels; PDF inspection applies additional per-page bounds. Each extraction uses a three-minute cancelable timeout. Tesseract gets OMP_THREAD_LIMIT=1, and child-process stderr is discarded to avoid leaking untrusted/private tool output into logs.

These are extraction limits, not the cryptographic format's maximum file size or every client upload limit. A document can be valid for encrypted storage and still be too large to OCR.

Plaintext lifetime

The in-memory export and tool input are plaintext while processing. PDF staging is also plaintext. Extractor.TempDir can select a private RAM-backed location, but default OS temporary storage need not be RAM. Ordinary cleanup is not guaranteed erasure after a crash, filesystem snapshot, or storage-device remanence.

This is the photocopier-room analogy: the archive remains encrypted at rest, but an authorized clerk must temporarily read a page to transcribe its text. The local tools, native parsers, and temporary directory are part of the trusted processing boundary.

Web reads synced indexes; it does not run this OCR pipeline or build content indexes itself.

Encrypted keyword indexes and ranked search

Klefki builds a term-frequency index locally, encrypts it as an ordinary internal document, and syncs it through the same revision protocol. Another client can search the index without repeating PDF extraction or OCR.

The library-catalog analogy

An archive clerk reads documents and writes a catalog listing which words occur in each one and how often. The clerk locks the catalog before sending it to another archive. The courier can deliver it but cannot use it to search the collection. An unlocked client opens the catalog and ranks results locally.

This is not a server-searchable encryption scheme. A client decrypts the index while searching. Term frequencies can reveal private information, so the catalog itself must be encrypted.

Building the index

search.Build snapshots current document heads, excluding internal sidecars and documents hidden under trash. For each supported document it exports authenticated content, extracts text, and counts terms from filename, tags, and extracted text. Unsupported formats still contribute name and tag terms.

The serialized index contains version, extraction language, and document entries identifying object/revision, term counts, and document length. The index payload is bounded to 32 MiB. A sidecar tagged klefki:system:search-index and an extraction-format tag is saved with Store.PutContext, giving it encrypted metadata, its own file key/chunks, and a pending revision.

The builder compares the selected documents with current heads again before publication. If documents changed during extraction, it returns a stale error rather than claiming its old catalog matches the new collection. Keyword and semantic sidecars publish separately; cancellation between them does not imply one atomic paired-index update.

Query terms and evidence

Query input is bounded to 4,096 bytes and 64 distinct tokenized terms. Query-only stop-word filtering removes common words without altering the stored index format. “Please show me the electricity bill” focuses on content-bearing terms rather than allowing common words to dominate.

The evidence gate normally needs one meaningful term for short queries. For longer queries it needs a stronger count, capped at three. A matching term containing a number can qualify directly, preserving useful exact references such as MTR9021 inside a long question.

BM25-style scoring

For each query term in each document, the implementation computes:

idf = ln(1 + (N - df + 0.5) / (df + 0.5))
contribution = idf × (tf × 2.2)
               / (tf + 1.2 × (0.25 + 0.75 × length/average_length))
score = sum(contributions for matching query terms)

N is document count; df counts documents containing the term; tf counts occurrences in this document. Rare words get more weight. Repeated words help with diminishing returns. Length normalization reduces the tendency for a huge document to win merely because it contains more words.

For intuition, if only one of ten bills contains MTR9021, that identifier has stronger distinguishing power than bill appearing in all ten. Exact scores depend on document lengths and frequencies, so this example describes ranking direction rather than a fixed expected number.

This implementation scans stored document term maps and computes scores in memory. It does not run SQL full-text search, Elasticsearch, or an inverted-index service on the server. That simplicity has a scaling tradeoff: query work grows with indexed documents and query terms, and loading/decrypting the index costs memory/time.

Staleness and fallback

Loaded index entries must correspond to visible revisions. A stale index is not silently treated as current content evidence. Desktop can rebuild missing/stale indexes and indexes imports. Browser uploads retain name/tag coverage until a desktop/CLI builds content indexes and syncs them.

Tied scores are ordered by revision ID for reproducibility. Search scores rank candidates; they are not probabilities that a document is correct.

Local embeddings, ONNX inference, and hybrid search

Keyword search asks whether words match. Semantic search compares learned vector representations so related wording can match. Klefki runs inference locally; it does not send documents or queries to a hosted AI provider.

The coordinate-map analogy

Imagine placing documents on a map where nearby coordinates represent related meaning. “Monthly electricity charge” and “utility invoice” may land nearby despite different words. Real embeddings have 384 coordinates, not two, and their geometry is learned rather than manually assigned.

The analogy helps explain similarity but cannot justify trust: nearby vectors do not prove the same identity, correct classification, or factual agreement. Embeddings can be misleading, particularly outside the model's language/domain.

Assets and model identity

The manifest pins BAAI/bge-small-en-v1.5 to an exact model revision, asset byte lengths, SHA-256 digests, tokenization/pooling settings, and runtime version. Model installation downloads public model assets or checks a local bundle; it does not upload vault data. Verify checks the expected files before native model use.

A fingerprint connects semantic indexes to their producing model/configuration. Comparing vectors from different models or tokenization settings as if they occupied the same space would produce meaningless scores even if both vectors had 384 elements.

Native inference is compiled with the onnx build tag. Without that tag, model_disabled.go explicitly returns unavailable. The inspected native support is Linux/Windows on amd64. It uses an ONNX Runtime shared library and a tokenizer; inference calls are serialized with a mutex and use bounded thread settings.

From text to a vector

Tokenization converts text into vocabulary IDs, not necessarily one token per word. The native model adds start/end tokens and constructs input_ids, attention_mask, and token_type_ids tensors. ONNX produces hidden-state output. The implementation uses CLS pooling and L2 normalization.

Long document text is split into 480-token windows with 64-token overlap, giving a 416-token stride. Overlap preserves phrases around boundaries. Maximum model token content is 510 before its two special tokens. The short embedding helper truncates to one window; the chunk helper covers long text with multiple windows.

Document sidecars retain name/content vectors, chunk vectors, label vectors, and related analysis data. They are encrypted internal documents under klefki:system:semantic-index. Vectors can leak meaning, so local model execution alone would not be enough if these vectors were stored or synced in plaintext.

Similarity and thresholds

For L2-normalized vectors, cosine similarity is their dot product:

similarity(q, d) = sum(q[i] × d[i])

Validation requires the correct dimension, finite values, and a norm near one. Semantic search scores a document against its content windows; short queries can also use its name vector. The current manifest uses an absolute cutoff of 0.52 and a relative cutoff of 0.90 × the best score, keeping only sufficiently strong nearby results.

For example, if the best score is 0.70, the effective cutoff is max(0.52, 0.63)=0.63. Scores 0.70 and 0.66 survive; 0.60 does not. These are illustrative numbers, not measured results from the bill fixture. A score of 0.70 does not mean “70% confidence.”

Hybrid ranking

Keyword and vector score scales differ. Klefki uses reciprocal rank fusion rather than adding raw BM25 and cosine values. Each list contributes by its result position:

RRF contribution = 1 / (61 + zero_based_position)

It considers at most 50 results per list and returns at most 20 fused hits. A document first in both lists gets 1/61 + 1/61; another first in one list alone gets 1/61. Weak semantic evidence is filtered before fusion because fusion discards the original similarity magnitude.

Browser inference and limits

The browser uses a worker and ONNX Runtime Web with verified model assets and synced document vectors. It embeds local queries rather than building OCR/document indexes. Native and browser implementations need compatible tokenization, model identity, and pooling.

The current browser worker selects the WebAssembly execution provider, sets one WASM thread, and resolves runtime assets under /models/runtime/. It loads the model/tokenizer from the fingerprinted cache and rechecks byte lengths and SHA-256 before use. A promise chain serializes worker messages. Input/output tensors are disposed and available typed-array buffers are cleared after inference. No GPU provider or hosted inference endpoint is selected by this worker.

Semantic processing is opt-in, English-first, and falls back through explicit unavailable/error handling rather than claiming a model exists in every build. Synthetic evaluation is recorded; private-document acceptance remains a separate open boundary.

Category suggestions, field extraction, and corrections

Document analysis builds suggestions from local embeddings and text patterns. It does not use a generative language model to invent a folder plan or silently rewrite metadata. The important engineering boundary is between proposing an interpretation and saving an edit.

Classification by label similarity

The built-in labels are Identity, Money, Legal, Health, Education, and Work. Each has a natural-language description embedded using the same model. Classification compares document vectors with these label vectors and looks at both the best score and its separation from the runner-up.

The default classification thresholds are cutoff 0.50 and margin 0.01, selected on the project's public synthetic evaluation. Those are different from search's 0.52/0.90 thresholds. A model can find a relevant search result without establishing a stable category winner.

Consider a document scoring Money=0.62 and Legal=0.615. The difference is 0.005, below a 0.01 margin. Despite a reasonably high best similarity, it is ambiguous. “Invoice attached to a legal settlement” plausibly belongs to multiple topics. The mechanism's uncertainty is appropriate evidence to review, not a reason to convert similarity into a percentage.

General-purpose field suggestions

core/semantic/fields.go extracts bounded date and currency patterns from text and attaches evidence. This is pattern recognition over strings, not a schema-specific guarantee that a particular date is a renewal deadline or that an amount is the payable total.

For example, finding ₹1,250 near bill text can suggest a currency amount. It does not by itself distinguish amount due, previous balance, or tax. A date near “issued” should not be promoted to expiry merely because both are dates. The system exposes generic evidence and permits corrections.

Corrections as sidecars

Saved corrections become encrypted internal documents tagged klefki:system:analysis-correction. They bind the interpreted logical object and content file ID, include confirmed category/fields, and can record resolved correction records. Content identity matters: renaming a PDF should not discard its correction, while replacing the PDF should not automatically reuse analysis for different bytes.

Multiple offline corrections can conflict too. The revision model is not exempt just because the payload is a model-related sidecar. Analysis loaders validate records, identity, and current content before using them.

Existing and custom tag matching

SuggestTags loads the keyword index, semantic index, visible document heads, and correction records. Candidates include built-in labels, existing user tags, and custom tags. A custom tag can have a description embedding and examples drawn from already tagged documents. Confirmed corrections can influence matching.

The source deduplicates candidates case-insensitively, checks reserved/user-tag rules, caps inputs/candidates, and skips conflicting or unsuitable documents. Existing tagged examples are tracked by object identity rather than counting multiple copies of the same owner as independent evidence.

Unmatched documents may be grouped and offered editable new tag suggestions using their semantic/term information. The system remains a suggestion engine; source-derived local clusters do not establish an objectively correct folder taxonomy.

Stale-plan protection and atomic application

A proposal refers to current revisions and session generation. Applying it after another edit or a lock/unlock cycle must not write to the wrong state. Desktop's organization service checks generation/revisions, and core/sync/tags.go applies validated tag changes transactionally.

Think of a librarian marking proposed labels on a review sheet. If the books have changed editions since the sheet was prepared, the librarian rechecks before sticking labels on them. Applying old suggestions without revision checks would be a lost-update bug.

The current organizer focuses on tags and document-purpose evaluation. The roadmap's broader vault/folder organization, local LLM features, and other future items are plans rather than existing capabilities inferred from this code.

Backup, restore, integrity checking, and safe export

Sync keeps devices aligned. A backup preserves a chosen local store independently of the server. These differ because deletion, bad edits, and server loss can propagate through replication, while an earlier separate snapshot may preserve recoverable history.

What a backup contains

The CLI backup directory contains account.v1 and a consistent local.db. The account file contains encrypted master wrappers; the database contains ciphertext, historical revisions, pending edits, folders, conflicts, and local bookkeeping. The random recovery key and unwrapped master key are not intentionally added to that snapshot.

A backup of device A does not include an unsynced edit that exists only on device B. Sync browser changes to a desktop/CLI store before backing them up. A ciphertext snapshot without an unlock route is not usable; a recovery code without the surviving wrapped records/ciphertext cannot recreate lost bytes.

Snapshotting correctly

Store.Snapshot serializes with sync and store operations and uses SQLite VACUUM INTO to create a consistent standalone database. It then publishes that file through the private non-overwriting helper. This handles WAL state correctly, unlike copying only a live database's main file.

The CLI opens an existing initialized store and checks account identity; it does not silently create an empty source. Restore rejects backup sources with nonempty WAL/journal state because it expects a completed snapshot rather than a live database.

The analogy is photographing a complete ledger at one instant. Copying random pages while entries are being posted can yield a plausible-looking but incomplete ledger.

Two integrity layers

Store.Check first uses SQLite PRAGMA integrity_check. That establishes database-structure integrity, not document authenticity. It then traverses stored revisions in insertion order, validates base ownership, authenticates each metadata/key pair, checks chunk counts, authenticates every chunk, and verifies lengths/final markers.

It also compares expected unique file chunks with all stored chunk rows, so unexplained extras do not pass unnoticed. Metadata-only revisions can refer to the same content file; expected chunks are counted by unique file ID.

This authenticates stored current and historical content, including retained trash. It cannot detect a complete valid branch erased before backup or a rollback to an older complete store. There is no trusted external historical checkpoint to compare with.

Restore workflow

The restore command unlocks the account from the backup using password or recovery code, creates a new destination, copies the snapshot, opens it as an existing store, and authenticates its contents before reporting completion. On ordinary failure it removes the newly created output directory.

Destinations must not exist. Recovery is a local decryption operation; it does not reset remote authentication or make a new server reconstruct deleted data. Keep the recovery code separate from backups that it can unlock.

Safe plaintext publication

local.Publish creates a private staging file in the destination directory, runs the writer, syncs and closes it, and hard-links it into the final path without overwrite. If authentication or writing fails, the requested final output does not become a partially decrypted file. Existing targets are refused.

Using a hard link makes publication exclusive. A filesystem without suitable hard-link support fails rather than quietly falling back to overwriting. A process crash can leave a private staging file; ordinary cleanup is not a universal crash-erasure guarantee.

export-plain deliberately writes plaintext documents and a metadata manifest. It uses opaque revision IDs as output filenames so hostile or colliding decrypted names are not interpreted as filesystem paths. This export includes historical content and trash; its privacy properties differ from encrypted backup.

Security boundaries, testing, and deployment mechanics

The strongest way to understand the project is to identify its invariants, then ask which checks establish each one. A build proves the code compiles; it does not prove a fingerprint reader works, a restore preserves your documents, or a hosted server runs the same revision.

Threat boundaries

Event Intended defense Remaining boundary
Server disk theft Encrypted documents, metadata, keys and sidecars Password guessing and visible structural metadata
Altered chunk AEAD context plus stream completeness Whole valid historical replay remains possible
Interrupted local import Atomic store transaction Hardware/crash behavior is wider than ordinary error tests
Lost upload response Immutable idempotent retry Server availability and storage loss remain possible
Concurrent offline edits Preserve multiple heads No automatic semantic merge or authenticated global graph
Locked local store theft Wrapped keys and ciphertext records OS memory/swap/keyring and weak passwords
Malicious browser origin No independent protection from supplied malicious code Origin controls executable client code
Logical permanent deletion Current object fences and cleanup Offline copies, backups and forensic erasure

The server can observe opaque IDs, size, timing, sessions, and some revision/delivery relationships. Encryption does not hide every column or traffic pattern. TLS secures transport; record AEAD secures content/context; transactions secure local publication boundaries. None replaces the others.

Cross-language test vectors

Go and TypeScript need exactly the same KDF output, envelope bytes, integer encoding, nonce handling, and rejection behavior. testvectors supplies public synthetic secrets and fixtures for both implementations. Fixed test keys/nonces are useful there but must never become production defaults.

The vectors act like a shared ruler: two independent implementations measure the same record and must agree. Passing vectors establishes those cases, not an audit of every parser or runtime integration.

Failure-oriented tests

Crypto tests cover tampering, malformed metadata, chunks, descriptor/recovery rules, and fuzz parsers. Sync/server tests exercise conflicts, resumability, retries, durable cursors, account scope, relay cleanup, batching, concurrency, and status. Backup tests cover snapshot/restore checking. Search tests use controlled extraction fixtures and labelled retrieval/semantic evaluations.

Good failure tests target invariants. For example, corrupting the last chunk should fail before a file becomes visible or a cursor advances. Repeating an identical revision publication should not append a duplicate event. Concurrent edits should preserve both heads. A structural SQLite check should not substitute for authenticating ciphertext.

This guide's validation covers the book/reader. Application checks, hosted deployment, and physical-device acceptance require their own evidence; this documentation review does not establish them.

Deployment mechanics

The base Dockerfile builds a Go server and runs it as a nonroot user with a data directory and TLS listener configuration. The web-serving deployment has separate packaging/model requirements; inspect its actual Docker/hosting files rather than assuming the base server image includes all client assets.

compose.yaml attaches the named klefki-data volume at /data, mounts TLS files read-only, binds the listener to host loopback, drops capabilities, and uses a read-only container root filesystem. Its writable data volume is where database and blob persistence belong.

Dockerfile.render instead uses a Node build stage to download verified model assets and compile the web client, a Go stage for the server, and a final image containing /web plus the server executable. Its command selects the hosting-provided port, serves /web, enables proxy-HTTP mode, and sets the relay queue limit from an environment variable. render.yaml selects that image and /healthz. These are source configuration facts, not a live deployment-state check.

Persistent mode requires persistent database/blob storage. An ephemeral host can lose both on restart. Temporary relay can be reseeded by linked devices retaining history, but it is not an automatic server backup service.

When adding protocol extensions, deploy a compatible server before clients that need them. The relay optimization retained older endpoints and client fallbacks. Current permanent deletion instead checks capability before allowing a bound store to rely on deletion, because an old server ignoring deletion fences could reintroduce records.

What remains outside proof

No external cryptographic audit is recorded. Anti-rollback/fork detection, shared libraries, mobile native apps, and broader future features are not implied by current encrypted sync. Read milestone evidence and the roadmap separately from implementation source.

One document end to end, source routes, and glossary

This chapter ties the mechanisms together. The example uses symbolic IDs for clarity; real IDs are random nonzero lowercase 32-hex values, and real ciphertext/nonces are not deterministic.

Follow the 9 MiB bill

Create the archive. Client A creates account A, random master key M, recovery key R, and KDF descriptor D. Password-derived KEK seals M; R seals another copy of M. The 260-byte account file can travel to another trusted client because it contains wrappers rather than M in plaintext.

Import. electricity-bill.pdf gets object O, revision V0, file F0, and key K0. Metadata says type=file, name, parent=the Bills object, tags, size=9,437,184, and count=3. Metadata is encrypted under M with O as context. K0 is wrapped under M with F0 as context. Three chunk records use K0 and authenticate account A, F0, indices 0–2, lengths, and final state.

Commit offline. The store saves these records and pending=1 in one transaction. A failed network connection cannot undo this completed import. The source PDF still exists independently; the encrypted database does not become a filesystem move operation.

Register and push. Client A derives a server credential from the auth half of the KDF output and obtains a scoped session. It inventories F0 chunks, uploads the missing ones, and publishes V0. It clears pending only after publication succeeds.

Receive. Client B starts from its local cursor and downloads V0. It unlocks the same M from the copied encrypted account. It verifies metadata under O, unwraps K0 under F0, verifies all three chunk records, and commits records plus cursor. Only then does B acknowledge receipt. In relay mode, cleanup can use durable delivery requirements; persistent mode retains server content.

Rename without re-encrypting bytes. B creates V1 based on V0, changing only the name. F0, K0's wrapper, and content chunks stay associated with the unchanged content. A fresh metadata nonce protects the new metadata record.

Create a conflict. A was offline and creates V2 from V0. After replication, V1 and V2 are heads of O. Upload order does not decide the winner. They are two visible editions with the original authenticated metadata of each branch.

Index. Desktop/CLI select current visible heads, export authenticated bytes, and use Poppler/Tesseract for the PDF. The word MTR9021 enters an encrypted keyword sidecar. Optional local BGE inference turns text windows into 384-dimensional vectors in a semantic sidecar. These sidecars travel through ordinary encryption/sync.

Query. “MTR9021 electricity” gets lexical evidence and BM25-style ranking. “The charge for powering my house” may get semantic candidates if the enabled model/index supports it. Hybrid mode filters weak semantic evidence and fuses ranks. Neither route needs server plaintext search.

Back up. The CLI snapshots a selected synchronized local store with VACUUM INTO, verifies all retained revisions/chunks, and saves encrypted account/database files. Recovery restores access locally if the password is lost and R plus wrappers/ciphertext survive.

Trash/delete. Trash first changes encrypted parent/timestamp metadata so restoration is possible. Permanent deletion later records an object fence, checks expected heads, removes local object history/chunks, and propagates the fence. Older independent backups still retain whatever they contained.

Questions to test your mental model

  1. Can a valid first chunk prove the whole bill arrived? No; completeness needs expected count, lengths, final marker, and whole-stream checks.
  2. Can a server credential decrypt documents? Not directly; it authorizes server access and differs from the master key.
  3. Can recovery reconstruct a deleted file? No; recovery unwraps a surviving key, not missing ciphertext.
  4. Does sync success mean no conflicts? No; preserving conflict copies can be correct successful sync.
  5. Is a synced word index private? At rest/in transfer its payload is encrypted; an unlocked client decrypts it to search.
  6. Does a cosine score of 0.8 mean 80% accuracy? No; similarity and calibrated probability are different quantities.
  7. Does building an ONNX binary prove the model works on your private PDFs? No; model assets, runtime acceptance, OCR quality, and collection-specific evaluation remain distinct.
  8. Does permanent deletion erase an older backup? No; each independently stored copy has its own lifetime.
